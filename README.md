The Go implementation of [XiHan Spec](https://github.com/XiHanFun/framework-spec): the primitives layer, manifests, the invocation context, the pipeline, operation contracts and the out-of-process plugin runtime. Use it to write Go plugins that run in the .NET host ([XiHan.Framework](https://github.com/XiHanFun/XiHan.Framework)), or to use the same primitives in Go applications; the spec lives in `spec/` as a submodule, and conformance is verified by the vectors and black-box runner of the spec repository.

## Modules

| Package | Contents | Spec |
| --- | --- | --- |
| `primitives` | `Error` / error codes, `Result[T]`, `Maybe[T]`, `ID[Tag, V]`, `LifecycleState`, `PipelineStage`, `Stability`, Baggage keys, message keys and templates, `FrameworkError` | RFC-0001, RFC-0010, `conventions/` |
| `manifest` | The `xihan.manifest.json` model, reading, canonical output and validation, capability declarations and requirement text | RFC-0002, `manifest/manifest.schema.json` |

| `pipeline` | The eleven-stage `Builder`: `Use` / `UseAt` / `UseNamedInstance`, `Before` / `After`, `Describe` / `Dump`, `Build`; ordering rules and error codes `KERNEL_PIPELINE_00x` | RFC-0004 |
| `operation` | `Contract`, `Schema`, `Handler[Req, Res]`, `Registry`, and an `Invoker` that executes through the full pipeline (XGI: JSON request and response) | RFC-0011 |
| `plugin` | The out-of-process plugin runtime `Serve`: environment variables, listening (a unix socket in a private directory / tcp / npipe), the handshake line, the `xihan.plugin.v1` server (checking the host's session token on every call), the lifecycle state machine and health push, event delivery, the host callback client `Host`, JSON logs the host can parse, message catalogs | RFC-0017, `plugin/` |
| `plugin/v1` | Protocol code generated from `spec/plugin/plugin.proto` (`buf generate`) | `plugin/plugin.proto` |
| `examples/echo` | An echo plugin: operations, subscriptions, health, configuration, host callbacks; `cmd/echo-go` is the executable entry point | — |

## Getting Started

```bash
go get github.com/xihanfun/framework-sdk-go
```

### Write a Plugin

```go
package main

import (
	"context"
	_ "embed"
	"os"

	"github.com/xihanfun/framework-sdk-go/invocation"
	"github.com/xihanfun/framework-sdk-go/operation"
	"github.com/xihanfun/framework-sdk-go/plugin"
	"github.com/xihanfun/framework-sdk-go/primitives"
)

//go:embed xihan.manifest.json
var manifest []byte

type CreateRequest struct{ Text string `json:"text"` }
type CreateResponse struct{ Text, Tenant string }

func main() {
	registry := operation.NewRegistry()
	_ = operation.Add(registry, operation.Contract{ID: "echoes.create", Stability: primitives.Experimental, Expose: []string{operation.ExposeHTTP}},
		operation.HandlerFunc[CreateRequest, CreateResponse](func(ctx *invocation.Context, request CreateRequest) primitives.Result[CreateResponse] {
			return primitives.Ok(CreateResponse{Text: request.Text, Tenant: ctx.Tenant()})
		}), nil, "")

	if err := plugin.Serve(context.Background(), plugin.Options{Manifest: manifest, Operations: registry}); err != nil {
		os.Exit(1)
	}
}
```

1. The manifest `xihan.manifest.json`: `kind: plugin`, `isolation: out-of-process`, `contributes.operations` lists every operation, and `entry` is the executable file name. Do not write `contributes.pipeline` (only Wasm plugins can contribute middleware; `plugin.Serve` rejects it when it is non-empty, as the host does when discovering plugins; `manifest.Read`, following .NET's `ManifestReader`, does not check this rule). Put the same file in the build output directory: the host reads it, and the runtime sends it verbatim during the handshake.
2. Register operations with `operation.Add`; requests and responses are plain JSON structs. Recoverable failures return `primitives.Fail`, error codes follow `<DOMAIN>_<KIND>_<NNN>` with the domain in upper case, and text uses message keys plus `Localization/<locale>.json` loaded by `plugin.LoadCatalog`.
3. Subscriptions, lifecycle callbacks and health items are wired in through `plugin.Options`. In the `Configure` callback, read the configuration section with `configuration.Decode(&settings)` (the host sends numbers and booleans as strings, converted by field type). In an operation, call back into the host with `plugin.HostOf(ctx)` (`Invoke` runs through the host's full pipeline, `Publish` goes through the host's message broker); permissions are declared in the manifest's `permissions` and granted by the host. A subscription's `Mode` selects the subscription mode (RFC-0009 "Subscription modes"): empty or `plugin.SubscriptionModeCompeting` is competing consumption, where only one of the host instances subscribed to the topic hands the message to the plugin; `plugin.SubscriptionModeBroadcast` is broadcast, where every online host instance hands it to its own plugin instance, best effort and without dead-lettering, suited to work every instance must do, such as clearing a local cache. A (topic, type) pair can be declared only once, not once in each mode, and `Serve` rejects this at startup; different types of the same topic can each use one mode, the host includes the mode of each delivery, and the runtime hands it only to the handlers declared with that mode.
4. Logs go to stderr: `slog.New(plugin.NewLogHandler(os.Stderr, slog.LevelInfo))`, which the host receives as structured logs; stdout carries only the handshake line.
5. `Serve` returns after the host closes stdin or calls `Stop`, and the process exits.

Verification: `xihan-conformance plugin --dir <output-dir>` (the black-box runner of the spec repository, `go install github.com/xihanfun/framework-spec/conformance/cmd/xihan-conformance@latest`). The tests in `examples/echo` run every case against `echo-go` this way. The runner carries its own generated protocol code, which cannot be linked into the same binary as this SDK's `plugin/v1`, so the tests run it as a separate process instead of importing its library.

### Use the Primitives in a Go Application

```go
ctx := invocation.Background(invocation.WithTimeout(2*time.Second), invocation.WithBaggage(map[string]string{primitives.BaggageTenant: "t1"}))
builder := pipeline.NewBuilder().UseAt(observe, primitives.Observe, pipeline.End, "app")
invoker, _ := operation.NewInvoker(registry, builder)
response := invoker.Invoke(ctx, operation.Request{ID: "orders.create", Payload: []byte(`{"quantity":2}`)})
```

`Result[T]`, `Error` and `Maybe[T]` share the JSON encoding of the .NET reference implementation (`{"ok":true,"value":…}` / `{"ok":false,"error":{…}}`), and the lifecycle transition table, the pipeline stage order, error codes and the Baggage key grammar are all verified by `spec/conformance/vectors`.

## Behavior Shared with the Host

The wire encoding of `Result` (RFC-0001): a success with a value is `{"ok":true,"value":…}`, where `value` is required and may be `null` only when the value type is `Maybe`; a success without a value (`Result[Unit]`, `Success()`) is `{"ok":true}`, without `value`; a failure is `{"ok":false,"error":{…}}`, where `error` is required and there is no `value`. On reading, a missing or non-boolean `ok`, a success with `error`, and a valueless success with `value` are all rejected, as are duplicate member names at any level (such as two `ok` members, or duplicates inside `value`, `details` or `inner`); member names are case-sensitive, and unknown members are ignored.

The wire encoding of `Error` (RFC-0001): members are written in the order `code`, `message`, `messageKey`, `details`, `inner`; `message` is always written, `messageKey` only when there is a key (`Literal` has none), and `details` is omitted when empty and `inner` when absent. On reading, `code` is required and must be valid, `message` is required and must be a non-empty string, `messageKey` must be valid when present, `details` must be a JSON object and `inner` must be an error object (`null` and arrays are both rejected); member names are case-sensitive, and unknown members are ignored.

JSON text that is read (the wire encodings of `Result` and `Error`, operation payloads, manifests) first passes one shared check (RFC-0001 "JSON text", ADR-0236): the syntax follows RFC 8259 (no comments, trailing commas, single quotes, `NaN` / `Infinity`, leading zeros, plus signs or multiple root values; empty text and whitespace-only text are not JSON either), the text is UTF-8, and a leading BOM is a syntax error; nesting is at most 64 levels (the outermost is level 1); strings and member names must be valid Unicode, so invalid UTF-8, overlong encodings, surrogates encoded as UTF-8, raw control characters, invalid escapes and lone surrogate escapes are all rejected; no level may have duplicate member names, compared after unescaping (`"a"` and `"\u0061"` are duplicates), while names that differ only in case are not duplicates. Syntax errors take precedence, with the location written only as `$`; otherwise the path of the first duplicate (the second occurrence of the member) is reported. `encoding/json` does not check for duplicate members, replaces lone surrogates with U+FFFD and has a nesting limit of 10000, so this step is done first by a check inside the SDK (`internal/jsontext`), which replays the same `json-text.json` as `rules.CheckJSONText` in the conformance module.

Numbers on the wire round-trip through the value model (the value models of RFC-0001 "Result" and RFC-0010 "Templates", ADR-0236): when the `details` of an `Error` (and likewise the JSON text of the plugin protocol's `Error.details`) is read by the value model, a number written as an integer within the signed 64-bit range is an `int64` and round-trips unchanged (`9007199254740993` does not become `9007199254740992`), any other number is a `float64`, and `1e400` is infinity; on writing, floats with integral values carry a decimal point (`2.0`, `-0.0`, and out-of-range values such as `1E+17`), so the other side still reads a float, a `float32` is first converted to the nearest `float64` (`float32(0.1)` is written as `0.10000000149011612`), unsigned integers beyond `int64` are written as floats, and `NaN` and infinities are written as the strings `"NaN"`, `"Infinity"` and `"-Infinity"`. Strings escape only the characters that must be escaped (`"`, `\`, control characters); `<`, `>`, `&` and non-ASCII characters are written as is. Typed values (`Result[Order]`, `Maybe[T]`, `ID[Tag, V]`) are decoded by the same rules as operation payloads, see "Operation Payloads" below; `Result[any]` and `any` inside values are arbitrary JSON, with numbers read as `json.Number` holding the original text and written back exactly as read.

### Operation Payloads

`operation.Invoker.Invoke` decodes the payload into the request type by RFC-0011 rule 2 (ADR-0236, matching the default read options of .NET's System.Text.Json rather than the habits of `encoding/json`). Every failure is `KERNEL_VALIDATION_001` + `kernel.operation.invalid_payload`, with `reason` set to the JSON path of the first problem:

- An empty payload is equivalent to `{}`; the shared check above runs first, with `$` for syntax errors and the path of the first duplicate for duplicate members; a payload of `null` gives `$`.
- Member names are case-sensitive (`encoding/json` is not), and unknown members are ignored; numbers are not read from strings, nor strings from numbers (except for fields tagged `json:",string"`).
- Integer fields accept neither decimal points nor exponents (`1.0` and `1e2` are not integers), and a value outside the range of the field type does not match (an `int32` field receiving `2147483648`); float fields accept integer notation, `1e400` overflows to infinity, `1e-400` is 0, and `float32` is read with the 32-bit range.
- `null`: strings, slices, arrays, maps, structs, pointers and `any` accept it as no value (the field keeps its zero value); integers, floats and booleans (including their slice items and map values) do not. To accept a `null` number or boolean, use a pointer (`*int64`, `*bool`).
- Required: a field tagged `xihan:"required"` is required (the counterpart of C#'s `required`); when it is missing, the path of the containing object is reported when that object ends (`$` at the root, nested ones like `$.inner`); only the member's presence is required, so a `null` value counts as present. Members without this tag take the zero value when missing.
- The first problem in text order is reported: a type mismatch written earlier is reported first, and a missing member in a nested object comes before a later type mismatch in the outer object.
- Types implementing `json.Unmarshaler` (`time.Time`, `json.RawMessage` and so on) get the original text to decode themselves, and a failure reports their path; types implementing `encoding.TextUnmarshaler` accept only strings; `any` is arbitrary JSON and keeps the value as read: numbers are read as `json.Number` holding the original text (`1e400`, integers beyond double precision, and the difference between `2.0` and `2` are all preserved), strings, booleans, `null`, `[]any` and `map[string]any` work as usual, and when a handler returns it unchanged, the JSON value of the response equals the original; `[]byte` reads a base64 string. Payload text is compared as JSON values; whitespace, member order, escapes and number notation are not part of the contract. For Go's own types that the spec does not cover (a supplement to ADR-0236): when a field is a non-empty interface (such as `io.Reader` or a custom `Shape` interface), decoding reports the path at that point; the SDK does not guess a concrete type, and polymorphic requests implement `UnmarshalJSON` on the type itself. When a user's own `UnmarshalJSON` returns an error, the path of the value it belongs to is reported, without locating anything inside that value (the SDK's own `Result`, `Maybe` and the like are exceptions and report paths inside). Field names, the promotion of embedded structs and `json` tags follow `encoding/json`.

```go
type CreateOrder struct {
	Customer string        `json:"customer" xihan:"required"` // required; null counts as present
	Note     string        `json:"note"`                       // optional; null means no value
	Quantity int32         `json:"quantity"`                   // optional; rejects null and 1.0
	Discount *float64      `json:"discount"`                   // optional; accepts null
	Lines    []OrderLine   `json:"lines"`
	Extra    any           `json:"extra"`                      // arbitrary JSON; numbers keep the original text
}
```

### Manifests

`manifest.Read` follows the check order and errors of RFC-0002 parsing rule 2 (ADR-0236, identical word for word to .NET's `ManifestReader`). Each step reports only the first problem, and every failure is a `*primitives.Error` with error code `KERNEL_CAPABILITY_006` (`manifest.ErrorCodeInvalidManifest`):

1. The shared JSON text check: text that is not JSON gives `kernel.manifest.invalid_json` with `reason` `$`; duplicate members give the same key, with `reason` the path of the first duplicate. `Read` does not skip a BOM; `ReadFile` reads UTF-8 and skips a leading UTF-8 BOM, and a missing file gives `kernel.manifest.file_missing` (argument `path`).
2. A `null` root: `kernel.manifest.empty`, with no arguments.
3. Checking item by item against the Schema: `kernel.manifest.invalid`, with `reason` the path of the first problem, such as `$.provides[0].version`. Members are taken in text order, each checked in turn for members outside the Schema (case-sensitive), `null`, type and value, descending into objects and arrays; once an object is done, missing members are checked in the order of `required`. Interface versions are positive integers without leading zeros, at most 2147483647, and only `requires[].version` may carry one `^`; middleware names are non-empty, stages and enums accept only lowercase names, `contributes.health` matches `^[a-z][a-z0-9.-]*$`, a duplicate in `contributes.permissions` reports the second occurrence, and `activation` has at least one item.
4. Cross-field constraints: a plugin without `isolation`, a non-plugin with `isolation` or `permissions`, duplicate `provides`, duplicate `requires`, and duplicate `bindings` names, in that order; the keys are `primitives.manifest.*`, and the only argument is `id`.

`Manifest.Validate` first checks the written shape of the manifest against the Schema, then the cross-field constraints, with code `PRIMITIVES_VALIDATION_001` (matching .NET's `Manifest.Validate`). The layout of `manifest.Write` is fixed (RFC-0002 "Writing"): two-space indentation, LF, no trailing newline, `": "`, empty arrays written as `[]`, a fixed member order, lists always written, `role` written as `provider` by default, `activation` written as `["onStartup"]` by default, a fixed `$schema`, and strings escaping only the characters that must be escaped; like .NET, it does not validate. The optional strings `Package`, `Entry` and `ConfigContribution.Schema` are `*string`: `nil` means not written and is omitted on output, while a pointer to an empty string means an empty string was written and is output as `"package": ""`; assign them with `manifest.Text("…")`.

### Message Templates

Template arguments are first mapped to the value model of RFC-0010 "Templates" (ADR-0236), which consists of null, boolean, string, 64-bit integer, double-precision float, array and object, and are then written according to the format specifier and locale; see [Language Mapping](#language-mapping) for how Go types map. Arrays and objects are written as compact JSON, with object members sorted by name in UTF-16 code unit order, nested `null` written as `null`, numbers written as at the top level, and containers deeper than 64 levels written as `null`. Format specifiers accept only `^[DdFfNnXx][0-9]{0,2}$`, so `E2`, `G`, `P`, `0.00`, `yyyy`, an empty specifier, one containing spaces, and `D100` are all written unformatted; `D` and `X` apply only to integers, `X` only to non-negative integers, and `F` and `N` to integers and floats, and on any other value they are written unformatted.

Formatting can take a locale: `primitives.FormatMessageIn(locale, template, arguments)`, `TryFormatMessageIn` and `FormatArgumentIn(locale, value, format)`, and `Catalog.Resolve` takes the symbols of the locale of the matched template (a template that falls back to en-US is written in en-US). A locale changes only the decimal separator and the group separator, taken from the spec's fixed table: de-DE, es-ES and pt-BR use `,` and `.`, fr-FR uses `,` and U+202F, ru-RU uses `,` and U+00A0, and en-US, zh-CN, zh-TW, ja-JP, ko-KR, locales outside the table and no locale all use `.` and `,`; locale names are case-insensitive. The decimal separator applies to unformatted floats (including the mantissa in exponent notation: `1.5e20` in de-DE is written `1,5E+20`) and to `F` and `N`, and the group separator only to `N`; unformatted integers are not grouped, `D`, `X` and numbers inside arrays and objects are unaffected by the locale, and neither are the minus sign, `NaN` and `Infinity`. The locale-free `FormatMessage`, `TryFormatMessage`, `FormatArgument`, `FormatValue` and `Describe` use the invariant culture.

### Built-in Steps of the Invoker

`operation.NewInvoker` adds three built-in steps to a copy of the pipeline passed in (RFC-0011 rule 10, ADR-0236). Their names match the .NET built-in middleware, and all of them have the owner `xihan.kernel.core` (`pipeline.KernelOwner`) and sit at the `Beginning` of their stage, ordered against other middleware at the same position by the RFC-0004 rules (ordinal order of owners, so `app` sorts before it):

- `ObserveMiddleware` in the Observe stage: translates panics in the middleware after it and in the handler to `KERNEL_UNEXPECTED_001` + `kernel.invocation.unhandled_exception`; panics in middleware before it (in the Ingress stage, or at the `Beginning` of the Observe stage with an owner that sorts before `xihan.kernel.core`) are passed to the caller as is.
- `DeadlineMiddleware` in the Resilience stage: if the deadline has already passed on entry, the result is `KERNEL_TIMEOUT_001` + `kernel.invocation.deadline_before_start`, and the later middleware and the handler do not run; cancellation is not checked on entry; timeouts and cancellation along the way are attributed by the deadline token.
- `ValidationMiddleware` in the Validate stage: raw invocations (`Invoker.Invoke`) decode the payload into the request here, failing with `KERNEL_VALIDATION_001`; typed invocations (`operation.Invoke`) skip it.

Before entering the pipeline, only an unregistered operation (`KERNEL_NOTFOUND_001`) and, for typed invocations, a type mismatch (`KERNEL_VALIDATION_002`) are checked, in that order. `Invoker.Invoke` encodes the response into a payload with `encoding/json` only after the pipeline finishes, so what middleware sees through `operation.ResponseOf(ctx)` is the response object before encoding; when it cannot be written (a float member that is `NaN` or infinite, a value serialization does not support such as a channel or function, or `MarshalJSON` failing or panicking), the invocation ends with `KERNEL_UNEXPECTED_001` + `kernel.invocation.unhandled_exception`, without a payload and without panicking, and a cause that is a `FrameworkError` goes into `inner`; `NaN` is not written as `null` or a string. The typed entry point `operation.Invoke` does not encode.

Cancellation and deadlines are signaled only through `ctx.Done()` and `ctx.Err()` (RFC-0003 rule 1, ADR-0236): the invoker, the built-in steps and the plugin runtime all run the handler synchronously on the caller's goroutine, without aborting it or abandoning it on another goroutine; when the handler returns a result as usual after the token fires, the invocation ends with that result, and attribution by the deadline token applies only when the handler writes the cancellation as its result (`KERNEL_CANCELLED_001`). Handlers should finish early by checking `ctx.Done()` themselves. `Invoker.Pipeline()` returns the pipeline actually executed (including the built-in steps).

## Language Mapping

When template arguments are mapped to the value model of RFC-0010 "Templates" (see [Message Templates](#message-templates)), Go types map as follows:

| Go value | Value model | Notes |
| --- | --- | --- |
| `nil`, `nil` pointers, `nil` slices and maps | Null | An empty string at the top level, `null` when nested |
| `bool` and types whose underlying type is `bool` | Boolean | `true` / `false` |
| `string` and types whose underlying type is `string` | String | As is |
| `int`, `int8`…`int64`, and `uint`…`uint64` within the int64 range | Integer | `rune` is `int32` and is written as an integer; use `string(r)` to write a character |
| `uint64` beyond int64, `*big.Int` | Float | `D` and `X` no longer apply |
| `float64`, `float32`, `*big.Float`, `*big.Rat` | Float | `float32` is converted to the nearest `float64`: `float32(0.1)` is written as `0.10000000149011612` |
| `json.Number`, `json.RawMessage` | Read as JSON | Integer notation within the 64-bit range is an integer; other numbers are floats |
| Slices, arrays (including `[]byte`) | Array | |
| Maps | Object | Keys are written as their text |
| Values implementing `error` / `fmt.Stringer` | String | Takes `Error()` / `String()`: `time.Time`, `time.Duration` and enums with `String` (`primitives.Stability`) all produce Go's own text |
| Everything else (structs, complex numbers and so on) | String | The text of `fmt.Sprint` |

Go's own text (dates, `Duration`, structs) does not carry across languages: when a plugin's catalog is to be formatted on the host, convert these values to strings before putting them in the arguments.

## Breaking Changes and Migration

This section lists the old behavior changed to align with the spec and the .NET reference implementation, and how callers should adapt.

- `Success()` / `Result[Unit]` encodes as `{"ok":true}`; the old version wrote `{"ok":true,"value":{}}`. Reading a `Result[Unit]` that has `value` (including `{}`) is rejected, with no compatibility path. Migration: parties that interoperate with old Go programs upgrade together; remove `"value":{}` wherever you build the JSON yourself. A success with a value that lacks `value`, or has a `null` `value` while the value type is not `Maybe`, was read as the zero value by the old version and is now rejected; use `Result[Maybe[T]]` for values that may be absent. On writing, a value that encodes as `null` (such as a `nil` pointer or a `nil` slice) while the value type is not `Maybe` is also an error; use a non-`nil` empty slice or empty map for empty collections.
- Kernel error codes, keys and arguments match .NET (the en-US default templates follow the .NET language files word for word and are obtained through `primitives.DefaultTemplate`; `Error.Message` uses them when the process's default resolver cannot resolve the message, then falls back to `Describe`):
  - The key for an invalid payload changes from `kernel.operation.payload_invalid` to `kernel.operation.invalid_payload`, and the arguments from `{reason}` to `{id, reason}`; `reason` carries only the JSON path of the error location (`$.quantity`, `$.lines[1].quantity`, `$['unit price']`, and `$` when the payload is `null`, is not an object, or fails at the root), no longer the `encoding/json` error text or Go type names (RFC-0011 rule 2). When a member name contains `.`, a space, `'`, `/`, `"`, `[`, `]`, `(`, `)`, `\`, a tab, a line feed, a carriage return, a form feed, a backspace, U+0085, U+2028 or U+2029, it is written as `['name']` with the name verbatim and unescaped, and an empty name is written as `$.`; a `null` that lands on an integer, float or boolean (which `encoding/json` silently treats as the zero value) also counts as a type mismatch (ADR-0235). New: `operation.InvalidPayload(id, reason)`. A host that translates by key finds no text for the old key.
  - A type mismatch in a typed invocation (`KERNEL_VALIDATION_002` + `kernel.operation.type_mismatch`) carries only `{id}` (ADR-0236), with the en-US template `Operation '{id}' was invoked with request or response types that do not match its registration.`; the `expected` and `actual` of the previous version were Go type names, which other languages cannot produce as the same arguments, so they have been removed. Migration: change code that reads `expected` / `actual` to use only `id`, and log the types at the call site yourself when you need them.
  - When middleware short-circuits with success and the handler produces no response, both JSON and typed invocations return `KERNEL_UNEXPECTED_001` (`kernel.operation.no_response`, argument `{id}`); the old version returned OK with an empty payload for JSON invocations. Migration: middleware that short-circuits with success either calls `next` or returns a failure.
  - Duplicate registration and a full registry in `operation.Add` now return `*primitives.Error` (`KERNEL_OPERATION_001` + `kernel.operation.duplicate`, arguments `{id, owner}`; `KERNEL_OPERATION_002` + `kernel.operation.registry_full`, argument `{capacity}`); the old version returned `*primitives.FrameworkError`. Migration: change `errors.As(err, &framework)` to `errors.As(err, &primitivesError)`; an invalid ID is still a `FrameworkError`.
  - The error for an uninitialized `Result` changes to `PRIMITIVES_VALIDATION_002` + `primitives.result.uninitialized`; the old version used text without a key.
  - The `message` of kernel errors changes from the `Describe` form (`kernel.operation.unknown (id=x)`) to en-US text (`Operation 'x' is not registered.`); match on error codes wherever you matched on text.
- `manifest.Read` reads strictly by the Schema: member names are case-sensitive (`encoding/json` is case-insensitive by default, so the old version also read `"ID"` into `id`); `null` is rejected anywhere (the old version treated it as absent); `primitives` and `provides[].version` may only be numeric strings, and only `requires[].version` may carry `^` (the old version accepted `^` in all three); the Schema's required members cannot be missing (the old version read a missing `stability` as `stable` and a missing `stage` as `ingress`); extra content after the JSON is rejected; duplicate member names at the same level are rejected (the old version took the last one); `activation` written as an empty array is rejected (the old version treated it as absent, and only absence means `onStartup`); `contributes.operations` follows the operation ID grammar (hyphens only between letters and digits). Migration: write manifests according to `spec/manifest/manifest.schema.json`, and change `"primitives": "^1"` to `"1"`.
- Pipeline ordering constraints follow RFC-0004 rule 7: either end of `Before` / `After` can be the instance name of a named instance, or the type name of a type registered with only one instance; a name that matches several registrations (several instances of one type referenced by type name, or an instance name equal to another type name) is `KERNEL_PIPELINE_003`. When errors are reported follows RFC-0004 rule 8 (ADR-0235): duplicate registration, an unknown stage (`KERNEL_PIPELINE_002`), and a constraint subject (the first argument) that is unregistered or ambiguous by name are reported immediately at registration; they are programming errors, and `UseAt` / `UseNamedInstance` / `Before` / `After` panic with a `FrameworkError` on the spot (as `http.ServeMux` does on a registration conflict). A constraint target that is unregistered or ambiguous, constraints across stages, and cycles are reported at sort time and returned by `Describe` / `Dump` / `Build`. The old version deferred all of these until `Describe` returned, and declaring a constraint before registering its subject also passed. Migration: register middleware before declaring its constraints (the target can still be registered after the constraint); code that registers middleware from dynamic data deduplicates before registering, or catches the `*primitives.FrameworkError` with `recover`.
- The values of registered Baggage keys are checked against conventions/baggage-keys.md (ADR-0204, ADR-0233): non-empty, at most 256 UTF-16 code units (characters outside the Basic Multilingual Plane count as two), and free of U+0000–U+001F and U+007F–U+009F. The entry point for external input (the option `invocation.WithBaggage`, which the plugin runtime also goes through when building a context from metadata) drops a member whose value does not conform and keeps the existing value of the same name; giving a registered key a non-conforming value when deriving in-program with `Context.WithBaggage(key, value)` is a programming error and, like a key that violates the grammar, panics with a `FrameworkError` (`PRIMITIVES_VALIDATION_001`, ADR-0235), neither dropping it silently nor keeping the existing value. The old version put the value into the context as is in both places. Migration: check values from outside with `primitives.IsBaggageEntryAcceptable` before deriving, or switch to the option `WithBaggage` so that non-conforming values are dropped; `xihan.idempotency-key` is the exception, left for the Idempotency stage to reject; unregistered keys are not checked here. New: `primitives.IsBaggageValueAcceptable`, `IsBaggageEntryAcceptable` and `MaxBaggageValueLength`. The plugin runtime drops such values accordingly when building a context from metadata.
- Trace flags follow RFC-0003 rule 7: without an upstream, `Context.TraceFlags()` is empty (this invocation is the root of the trace), where the old version always treated it as sampled; when `traceparent` is written, the flags carry only the sampled bit (`00` or `01`), an upstream `00` is passed down as is, and other bits do not enter the context (ADR-0235; the old version wrote flags such as `03` as is); without an upstream, the SDK has no sampler and writes `01`; `traceparent` accepts only version `00` and lowercase hexadecimal, and other versions such as `ff` are treated as absent (the old version accepted any two-digit version); `WithTrace` with IDs but no flags is treated as sampled. Whether a trace is sampled depends only on the lowest bit of the flags (`invocation.IsSampled`); the old version recognized only `01`, so `03` also counted as not sampled.
- `operation.Invoker` translates panics in middleware or handlers to `KERNEL_UNEXPECTED_001` (`kernel.invocation.unhandled_exception`, no arguments), matching how the .NET Observe stage translates unhandled exceptions (RFC-0011 rule 5, which rule 10 requires language SDKs to implement); the panic value and stack trace are written only to the `slog.Default()` log, and a value that is a `FrameworkError` is attached as the inner error. The old version did not recover panics, so the plugin process crashed with them. Handlers that need the process to exit use `os.Exit` instead.
- Timeouts and cancellation are attributed by the deadline token alone (RFC-0004, ADR-0092): `invocation.Context.Cancellation()` reports `KERNEL_TIMEOUT_001` once the deadline has passed, even if the caller cancelled first, and `KERNEL_CANCELLED_001` when the deadline token has not fired. The old version reported whichever fired first, so when the caller cancelled and the deadline then passed, it was still cancellation. New: `Context.DeadlineExceeded()`. The built-in step `DeadlineMiddleware` of `operation.Invoker` takes on the attribution of the .NET `DeadlineMiddleware`: if the deadline has already passed on entering the Resilience stage, the result is `KERNEL_TIMEOUT_001` (`kernel.invocation.deadline_before_start`); when downstream writes `KERNEL_CANCELLED_001` while the deadline token has fired, it is rewritten as `KERNEL_TIMEOUT_001`. Callers that decide retries by error code treat such invocations as timeouts.
- `operation.Current`, `RequestOf` and `ResponsePayloadOf` are visible only during the invocation, on the context passed down through the pipeline: per-invocation state (the descriptor, request, terminal and response payload) lives in a context derived for this invocation instead of the item bag, and after the invocation ends, the caller's context and item bag remain unchanged. The old version left them in the item bag and did not clear the terminal of typed invocations, so a later JSON invocation on the same context executed the previous typed terminal (a bug). Code that still reads these three on the caller's context after the invocation reads them in middleware instead.
- The parameters of `primitives.Unexpected` change to `(code, messageKey, details, inner)`, consistent with the other factories and `NewError` (RFC-0001, ADR-0137); the old order was `(code, messageKey, inner, details)`. The two parameters have different types, so old calls fail to compile; swapping the two arguments is enough.
- Template format specifiers change to a portable subset (RFC-0010) and are no longer interpreted as Go `fmt` verbs: `D[n]` (integer, zero-padded to at least n digits), `X[n]` / `x[n]` (hexadecimal of a non-negative integer), `F[n]` (fixed-point, 2 digits by default), `N[n]` (thousands separator `,`, decimal point `.`, 2 digits by default); F and N round on the exact decimal expansion of the value, and exact halves round to even (banker's rounding, matching .NET: 0.125 with `F2` gives `0.12`, and 2.5 with `F0` gives `2`). D, F and N are case-insensitive (`d3` equals `D3`; the old version treated lowercase as unsupported), and the precision is 0–2 digits after the letter (since ADR-0236, see below). Other specifiers (dates, custom numeric patterns) are .NET format strings, which the SDK writes unformatted. Migration: change `{count:%03d}` to `{count:D3}`, `{n:%x}` to `{n:x}`, and `{n:%.2f}` to `{n:F2}`; plugin catalogs are handed to the .NET host during the handshake and formatted by .NET rules, where the old `%` forms would be taken as custom numeric formats, so they must be changed.
- Templates support `{{` / `}}` escapes; placeholder names follow `^([A-Za-z][A-Za-z0-9_]*|[0-9]+)$`, so `{_x}`, which starts with an underscore, is no longer a placeholder but a literal; an unclosed `{` and the text after it are kept as is.
- `primitives.Catalog.Resolve` resolves strictly: when the key is not found or any placeholder lacks a value, it returns false, and `Error.Message` falls back to `Describe` accordingly; the old version still returned a partial translation when values were missing. Use `FormatMessage` directly for lenient formatting, and the new `TryFormatMessage` for strict formatting. Locale names are no longer compared case-sensitively.
- The text form of message arguments is unified in `primitives.FormatValue` (shared by templates and `Describe`, RFC-0010): `nil` and `nil` pointers are written as an empty string, where the old version wrote `<nil>`; floats with 1e-4 ≤ |x| < 1e17 or x = 0 are written as the shortest round-trip decimal without an exponent, so `2.0` is written `2` and 1e16 is written `10000000000000000`; outside that range they take exponent forms such as `1E+17`, `9.9E-05` and `5E-324`, negative zero is written `-0`, and NaN and infinities are written `NaN`, `Infinity` and `-Infinity` (ADR-0235). F and N write all integer digits, and a negative number that rounds to zero keeps its minus sign (`-0.00`). Code that relies on the old text (such as matching `<nil>` in logs) must change.
- Duplicate member names at the same level in `Result` and `Error` are invalid (ADR-0235); the old version let `encoding/json` take the last one. Reading `Error` is stricter: when `details` is `null` or an array, `inner` is `null`, `messageKey` violates the grammar (including an empty string), or `message` is missing, empty or not a string, `json.Unmarshal` returns `PRIMITIVES_VALIDATION_001`, where the old version silently ignored these. Senders only need to write the encoding described above; omit the `messageKey` member when it is empty.
- The shared JSON text check (RFC-0001 "JSON text", ADR-0236): when reading `Result` and `Error`, a leading BOM, nesting deeper than 64 levels, lone surrogate escapes (`"\ud800"`) and invalid UTF-8 are all rejected, where the old version let `encoding/json` accept them (replacing lone surrogates with U+FFFD). Operation payloads pass the same check first: the `reason` for syntax errors (including a BOM, nesting deeper than 64 levels and lone surrogates) is always `$`; a duplicate member at any level is `KERNEL_VALIDATION_001`, with `reason` the path of the first duplicate, reported before any other problem (the old version let `encoding/json` take the last one); a whitespace-only payload is no longer equivalent to `{}` (an empty payload is still equivalent to `{}`) and is handled as a syntax error. `manifest.Read` rejects these forms as well. Migration: send valid UTF-8 JSON, do not prefix the text with a BOM, and remove duplicate members from code that generates JSON.
- Numbers on the wire round-trip through the value model (ADR-0236): integers in the values of `Result[any]` and `Result[map[string]any]` and in `Error.Details` are read as `int64`, where the old version let `encoding/json` read them as `float64` (so integers beyond 2^53 lost precision); floats with integral values are written as `2.0` and `-0.0` (the old version wrote `2` and `-0`, which the other side read as integers); `NaN` and infinities are written as strings (the old version's `json.Marshal` failed, so the whole `Result` could not be written). The plugin protocol's `Error.details` is read and written by the same model; arrays and objects read back are `[]any` and `map[string]any`, and details that are not a valid JSON object are dropped. Typed values in `Result`, `Maybe` and `ID` switch to the SDK's decoding: member names are case-sensitive (the old version also read `"Count"` into `count`), integers do not accept `1.0`, integers and booleans do not accept `null`, and numbers are not read from strings. Migration: change code that asserts integers in details as `float64` to also accept `int64` (or take the text with `primitives.FormatValue`); senders write members by the JSON names of the fields.
- Operation payloads are decoded by RFC-0011 rule 2 (ADR-0236) instead of being handed to `encoding/json`: member names are case-sensitive (the old version also read `"Quantity"` into `quantity`); narrow integers such as `int32` are checked against their own range; `1e400` in a float field is read as infinity (the old version reported a type mismatch); `null` in the slice items and map values of integers, floats and booleans also reports a type mismatch; the required tag `xihan:"required"` is new; when several problems exist, the first in text order is reported, and missing required members are reported when their containing object ends. Migration: callers write members by the JSON names of the fields; numbers that must accept `null` become pointers; add `xihan:"required"` to members the contract requires.
- Reading and writing manifests matches .NET word for word (RFC-0002, ADR-0236): errors from `manifest.Read` and `ReadFile` change from `*primitives.FrameworkError` (`PRIMITIVES_VALIDATION_001`, with an English description) to `*primitives.Error` with code `KERNEL_CAPABILITY_006`, keys `kernel.manifest.invalid_json` / `empty` / `invalid` / `file_missing` or `primitives.manifest.*`, and only a path (`reason`), `path` or `id` as arguments; `Validate` also returns `*primitives.Error`. Interface versions above 2147483647 are rejected (the old version allowed up to the int limit; the same applies to `ParseRequirement` and `ParseDeclaration`); empty middleware names and a `contributes.health` that violates the grammar are now rejected. `ReadFile` skips a leading UTF-8 BOM, and `Read` does not. `Write` switches to the canonical layout: lists are always written (`[]`), `role` and `activation` are written with their default values, `requires[].optional` and `bindings[].required` are always written, strings no longer escape `<`, `>`, `&` and non-ASCII characters, `Write` no longer validates (like .NET), and `["onStartup"]` is written when `Activation` is an empty slice. The rule that only Wasm plugins can contribute middleware moves from `manifest.Read` to `plugin.Serve` (the .NET host checks it when discovering plugins, and `ManifestReader` does not). Migration: where you matched on error codes, use `errors.As(err, &primitivesError)` and look at `Code` and `MessageKey`; where you matched on the English description, look at the path; update the expected values of tests that compare written text.
- Template values are written by the value model (RFC-0010 "Templates", ADR-0236): arrays and objects are written as compact JSON (the old version used the `fmt.Sprint` forms `[1 a]` and `map[a:1]`); a `uint64` beyond int64 is a float (the old version wrote all digits, and `D` still zero-padded it); a `float32` is written by its `float64` value (`float32(0.1)` changes from `0.1` to `0.10000000149011612`); a `json.Number` in decimal notation is a float, `F` rounds on the binary value (`2.675` with `F2` changes from `2.68` to `2.67`), and `7.50` is written `7.5`. Format specifiers accept only `^[DdFfNnXx][0-9]{0,2}$`: the precision is at most two digits (the old version allowed up to 999), and `D` on a float (including `2.0`) is written unformatted (the old version zero-padded floats with integral values). Migration: convert values that need a fixed form to strings at the call site first; when you need more than two digits of precision, format in code instead. New: `FormatMessageIn`, `TryFormatMessageIn` and `FormatArgumentIn`; `Catalog.Resolve` writes the decimal and group separators of the locale of the matched template (the old version always used the invariant culture), so code that relies on the old text must change.
- The invoker's deadline check, decoding and exception translation become built-in steps in the pipeline (RFC-0011 rule 10, ADR-0236, revoking ADR-0235's "check the deadline before the first middleware"): when the deadline has already passed, middleware in the Ingress and Observe stages still runs, and the invocation ends with `deadline_before_start` only at the Resilience stage (the old version ran no middleware at all); the payload is decoded only at the Validate stage, so failures of middleware before it (authentication, tenancy, authorization) are reported before an invalid payload (the old version decoded before the handler, so an invalid payload was always found last, but invocations that failed authentication were also decoded first); panics in middleware in the Ingress stage, or at the `Beginning` of the Observe stage with an owner that sorts before `xihan.kernel.core`, are passed to the caller as is (the old version always translated them). Middleware named `ObserveMiddleware`, `DeadlineMiddleware` or `ValidationMiddleware` can no longer be registered in the pipeline. Migration: put work that must happen before the deadline check in the Ingress or Observe stage; put middleware whose panics should be translated at the `End` of the Observe stage or later; put middleware that uses the raw request object after the Validate stage.
- Optional manifest strings become pointers (a supplement to ADR-0236): `Manifest.Package`, `Manifest.Entry` and `ConfigContribution.Schema` change from `string` to `*string`, which tells "written as an empty string" apart from "not written"; when an empty string was written, `Write` writes `"package": ""`, matching .NET (the old version always omitted empty strings). Migration: assign with `Package: manifest.Text("XiHan.Orders")`, check for `nil` before dereferencing when reading, and compare the pointed-to values when comparing two manifests.
- Messages of pipeline configuration errors change to the original English text of .NET (RFC-0004 rule 8, a supplement to ADR-0236), identical word for word across languages: for example `Middleware ordering constraints in stage 'validate' form a cycle: 'Guard[a]', 'Guard[b]'.` (a cycle lists all middleware still blocked, in baseline order, with instances registered by name written as `TypeName[name]`; the old version wrote only the stage), `The ordering constraint of middleware 'Guard[a]' references unregistered middleware 'zz'.` and `Unknown pipeline stage 'bogus'.`. Constraint targets are now resolved stage by stage, so a cycle in an earlier stage is reported before an unregistered constraint target in a later stage (the old version resolved all constraints first). Error codes are unchanged. Migration: match on error codes wherever you matched on message text.
- Arbitrary JSON keeps the value as read (RFC-0011 rule 2, a supplement to ADR-0236): for members of type `any` in payloads and `Result` values, numbers change from `int64` / `float64` to `json.Number` holding the original text (the previous version read them by the value model, so `2.0` was written back as `2`, and `1e400` was read as infinity and could not be written into a response). `Error.Details` and the error details of the plugin protocol are still read by the value model as `int64` / `float64`. Migration: change code that type-asserts numbers in `any` to assert `json.Number`, then take the value with `Int64()` / `Float64()`.
- Responses are encoded after the pipeline finishes (RFC-0011 rule 10 "Encoding", a supplement to ADR-0236): middleware no longer has a payload; `operation.ResponsePayloadOf` is removed in favor of `operation.ResponseOf(ctx)`, which returns the response object before encoding (typed invocations have it too); a response that cannot be written changes from `KERNEL_UNEXPECTED_001` with keyless English text to `kernel.invocation.unhandled_exception`, the cause goes only to the log, framework errors go into `inner`, and panics in `MarshalJSON` are caught as well. Migration: middleware that reads the response payload in Egress reads the object from `ResponseOf` instead, and encodes it itself when it needs text.
